# The base encoder — a waypoint, kept as a record

**This is detail. The summary lives in [docs/04-model.md](04-model.md); read that first.**

`deberta-v3-base` (184M) was the first architecture Airlock trained, and every methodological
finding in this project came out of it. It is **not a deliverable** — the shipped comparison runs
on micro / large / generative — but the results are recorded here because they are the evidence
for why the project moved on, and because the model can be rebuilt exactly from this page.

---

## Why it existed, and why the project moved past it

Chosen under [decision 006](../DECISIONS/006-model-architecture.md) when the brief's fork was
still "encoder vs generative" and the hardware premise was still a laptop. It was the smallest
thing that could answer the question.

Two things changed:

1. **[Decision 012](../DECISIONS/012-the-premise-is-a-trust-boundary-not-a-laptop.md)** replaced
   "must run on a laptop" with "must run inside the company's trust boundary". The 372MB ceiling
   that made `base` the natural pick stopped being load-bearing, so a larger encoder became a
   legitimate arm rather than a violation of the thesis.
2. **The same decision reopened the generative branch**, which
   [decision 009](../DECISIONS/009-dropping-the-generative-branch.md) had closed on an inference
   cost that no longer applies.

`base` is kept in the comparison as a **capacity waypoint** — it is what sits between micro (22M)
and large (434M), and without it the size curve has a hole in the middle. Its weights are not a
project output.

## What it achieved

On real prose (2,492 CFPB narratives, 10,543 surrogate-filled spans), three seeds, trained on the
hardened injector:

| method | recall | precision | F1 | category accuracy |
|---|---:|---:|---:|---:|
| **base (hardened)** | 70.5% ±1.0 | **97.5% ±1.0** | **81.8% ±0.5** | 99.2% |
| presidio | **77.9%** | 52.8% | 62.9% | n/a |
| base (authored carriers) | 47.3% ±17.1 | 94.9% ±1.8 | 62.0% ±15.9 | 99.6% |
| spacy | 44.1% | 17.8% | 25.3% | n/a |
| regex | 3.5% | 7.4% | 4.8% | n/a |

In the M4 attack, on `natural_v2`:

| | U unique | PII removed | collateral |
|---|---:|---:|---:|
| raw text | 36.9% | 0.0% | 0.00% |
| **base (hardened)** | **0.2%** | **83.0%** | **0.40%** |
| presidio | 1.2% | 46.7% | 1.90% |
| spacy | 0.0% | 73.3% | 3.58% |

Inference on an M1: **5.0 narratives/sec**, 199 ms each, 4.8 GB peak, 744 MB on disk (fp32).

## What it taught the project — the part that outlived the model

Every one of these came from `base`, and all of them still hold:

1. **A model trained on marked CFPB text learns `XXXX → redact`.** Real text marks its own
   answers, so injection is the only viable training substrate (M1).
2. **A model trained on authored carrier sentences learns the phrasing, not the entity type.**
   `ORG_THIRD_PARTY` scored 0.1% on real prose while its surrogates were the same ten bank names
   it trained on ([decision 008](../DECISIONS/008-the-transfer-metric-was-invalid.md)).
3. **Held-out templates are not a sufficient control** when one author wrote them all. The gap
   looked reassuring at 8.7 points; real prose showed a 30-point collapse.
4. **Carriers mined from the corpus fix it.** Same architecture, same hyper-parameters, only the
   data changed: `ORG_THIRD_PARTY` 0.1% → 45.0%, and seed-to-seed variance collapsed from ±17.1
   to ±1.0 ([decision 010](../DECISIONS/010-hardening-the-injector.md)).
5. **`TEMPORAL` is the control nobody designed.** The one well-powered category that received no
   real carriers is the only one that did not improve — treatment applied, large gains; treatment
   withheld, nothing.
6. **A re-identification rate alone rewards over-redaction.** spaCy's 0.0% leak comes with 3.58%
   collateral damage, which is the difference between a redactor and a shredder.

## Rebuilding it exactly

Everything needed, so the weights do not have to be kept:

```bash
python scripts/m3_train_encoder.py \
    --model microsoft/deberta-v3-base \
    --train-set train_hard2 \
    --out encoder-base \
    --seed 20260806 \
    --batch 8 \
    --bf16
```

| | |
|---|---|
| base model | `microsoft/deberta-v3-base` |
| task | token classification, BIO over the 16 categories in [DEFINITIONS.md](../DEFINITIONS.md) |
| labels | 33 (`O` plus `B-`/`I-` per category) |
| training data | `data/synthetic/injected_train_hard2.parquet`, regenerated by `make m2` |
| seeds | 20260806, 20260807, 20260808 |
| epochs | 3 · batch 8 × 2 grad-accum · lr 3e-5 · warmup 0.06 · max len 384 |
| precision | **fp32 or bf16 — never fp16, see below** |
| hardware | trained on a rented RTX 3090; ~12 min per run |

**The fp16 trap, which is the one thing that will silently ruin a rebuild.** transformers 5.x
loads a checkpoint in the dtype it was *saved* in, and the `deberta-v3-base` checkpoint on the Hub
is stored in **float16**. Training it as-is produces `nan` from the first optimiser step —
gradients stay finite, then every parameter goes non-finite after `step()`. The tell is a loss of
exactly `4.8046875`, which is exactly representable in fp16.

`scripts/m3_train_encoder.py` forces `dtype=torch.float32` and asserts it. Without that, the run
completes, saves a plausible 744MB model, and reports numbers from a model that learned nothing.

---

## Why the weights are not kept

They are ~712MB per seed, ~2.1GB for the three, and they are fully reconstructible from the recipe
above. Nothing downstream depends on them: the shipped comparison uses micro, large and
generative, and `make repro` regenerates the training data before training anything.

The weights have **not been deleted** from the working tree — they are gitignored and harmless
where they sit, and deleting them is the user's call rather than a cleanup step to take
unilaterally. `models/encoder-hard-s*` can be removed at any time to reclaim the space.
